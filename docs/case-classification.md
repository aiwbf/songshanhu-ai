# Case Classification

## Rule First

`classify_case(profile, question)` 先走规则，不依赖 embedding。

- 先识别操作型问题：
  - `房产锁定`
  - `房产解锁`
  - `单位账号注册与审核`
  - `报名资料修改`
- 再识别特殊对象：
  - `华侨华人`
  - `台湾学生`
  - `香港/澳门学童`
  - `优才卡`
  - `优粤卡`
  - `荣誉市民`
- 最后判断常规招生类别：
  - `A1 / A2 / A3 / B1 / B2 / B3 / C`

## Minimal Follow-Up Fields

系统只追问最少必要字段：

- 学段
- 学童户籍
- 监护人户籍
- 工作地
- 房产所在地
- 是否属于人才/优待对象
- 是否为单位管理员
- 是否为转学/非起始年级

只有在这些字段足够后仍无法稳定落类时，才追加更细字段，例如：

- 单位是否具备 B1 指标
- 户籍类型（家庭户 / 集体户）
- 房产权属关系

## Core Classification Rules

### A 类

- `A1`
  - 学童为松山湖家庭户
  - 房产在松山湖
  - 房产权属关系不落入“非直系亲属”例外
- `A2`
  - 学童为松山湖集体户
  - 监护人当前仍在松山湖工作
- `A3`
  - 学童为松山湖户籍，但不满足 A1 / A2

### B 类

- `B1`
  - 学童为非东莞或港澳户籍
  - 监护人在松山湖工作
  - 单位有 B1 指标 / 入学名额
- `B2`
  - 监护人在松山湖工作
  - 命中优待 / 人才规则，如优才卡、优粤卡、荣誉市民、人才职称等
- `B3`
  - 监护人在松山湖工作
  - 未命中 B2
  - 仍具备企业积分制人才路线的可能

### C 类

- 学童为非东莞 / 港澳台户籍
- 家庭与松山湖存在工作地 / 居住地 / 户籍地 / 房产关联

## Explainability

所有分类结果都返回 `reason_chain`，面向开发排查。示例：

- `学童为松山湖家庭户且房产在松山湖，满足 A1 基本条件。`
- `监护人在园区工作且具有人才/优待身份，命中 B2。`
- `当前资料不足以稳定落类，先补最少必要信息再下最终结论。`
